# Tangible Therapy website — read this first

This is the context for editing the live website for Tangible Therapy (tangiblementalhealth.com), a therapy practice in Utah with offices in Orem, Provo and Sandy. The site is a static Astro 5 site in the private GitHub repo tangible-therapy/tangible-website, hosted on Netlify. It was rebuilt from Squarespace in October 2026. The same docs live in the repo as CLAUDE.md (short pointer) and docs/context/website-context.md (this file). The owner keeps a copy as the project file "Website context - read first"; Claude keeps that copy in sync itself (rule 8).

## Non-negotiable rules

1. Preview first, always. Work on a new branch, open a pull request, and give the user the Netlify Deploy Preview link. Only merge to main after the user approves. Merging to main publishes to the live site automatically.
2. Never deploy to Netlify directly (no `netlify deploy`, no drag-and-drop, no editing in the Netlify UI). GitHub main is the only source of truth; Netlify builds from it.
3. Never put passwords, logins, API keys or personal data in the repo. The staff password lives only in Netlify's STAFF_PASSWORD environment variable. Point people to the team password manager instead.
4. Don't break URLs. If a page is renamed or removed, add a 301 redirect in netlify.toml. Keep the existing ~90 redirects (they protect SEO from the Squarespace move).
5. Check desktop and mobile before handing over a preview (1440px and 390px wide at minimum, also ~1280 and ~1024). Blocks are placed on a grid and can overlap.
6. Run `npm run build` before pushing; it must finish with no errors.
7. Claude must not type passwords/credentials, create accounts, or approve Google/OAuth permissions for the user — ask the user to do those steps.
8. Keep the context docs current automatically — don't wait to be asked. Before opening (and again before merging) any pull request, check whether the change makes anything in CLAUDE.md, docs/context/website-context.md or docs/context/chatbot.md wrong or incomplete (how a feature works, where something lives, new/removed pages, forms, quizzes, roles, env vars, scripts, alert recipients, dates in "Status and open items"). If so, update those docs in the SAME pull request and say so in the PR summary. Then, right after the pull request is merged to main, copy the merged docs/context/website-context.md into the claude.ai project file "Website context - read first" (Projects tool, project_write to that file's existing path, replacing it in place). If the chat has no project access, tell the owner to refresh that file. Example: the orientation quizzes moving from Google Forms to on-page quizzes (PR #36) changed sections 4 and 5 and should have shipped with the doc update.

## How pages are built (important)
Most pages were converted from Squarespace's Fluid Engine layout and keep its grid: a section `<section class="sec t-light ...">` contains `<div class="fe" style="--rows:16;--mrows:24">` and blocks like `<div class="b b-html" style="--d:3/2/14/10;--m:2/2/7/10;--dz:2;--mz:2">`.
- sec t-* = colour theme (t-white, t-white-bold, t-light, t-bright, t-bright-inverse, t-dark, t-black...), defined as CSS variables in global.css.
- .fe = grid: desktop 26 tracks (gutter + 24 columns + gutter), mobile 10 (gutter + 8 + gutter).
- Each block has --d (desktop) and --m (mobile) grid-area as rowStart/colStart/rowEnd/colEnd, plus --dz/--mz z-index. .b.jc / .b.je centre or bottom-align; inset-m adds mobile padding over shapes.
- OVERLAP GOTCHA: if a block starts on a row another text block still occupies, text overlaps at some widths. Fix by starting the lower block on the row after the upper block ends (for the breakpoint that overlaps), or by putting heading + paragraph in one block. Check 1440, ~1280, ~1024 and 390px.
- Newer sections are plain HTML/CSS (no grid): blog landing, contact page, careers job list, footer, Ready to book (BookCTA.astro), orientation, the /ceu "Our Next Live Training" section (.ceu-live). Prefer this simpler style for new sections.

# 2. Editing workflow (preview first)
1. git checkout main && git pull; create a branch (e.g. update-sarah-bio).
2. Make the change; npm install (first time) and npm run build must succeed. Update the context docs in the same branch if the change affects them (rule 8).
3. Check desktop (1440px) and mobile (390px).
4. Commit, push the branch, open a pull request into main. Netlify builds a Deploy Preview and posts the link on the PR. Give the user that link plus a plain-English summary.
5. Only after the user approves: merge to main. Netlify publishes main automatically (~30 seconds). If the docs changed in that PR, update the project file "Website context - read first" straight away (rule 8).
6. If something goes wrong after publishing: revert the PR on GitHub, or use Netlify > Deploys > publish an earlier deploy.
Do not: run netlify deploy, upload to Netlify by hand, commit directly to main (unless the user explicitly says to skip the preview), edit dist/, or reintroduce Netlify Forms (data-netlify).
Notes: staff pages need the staff password on previews (Claude won't have it) - check them locally with npm run build. Team members get access by being added as collaborators on the GitHub repo and starting chats with the repo attached. No CMS is installed; the owner prefers changes go through Claude.

## Staff accounts (Google sign-in) — built Oct 2026, being switched on in stages
The staff gate has two modes, chosen by the Netlify environment variable STAFF_AUTH:
- STAFF_AUTH=google: staff sign in at /staff-login with their Google @tangiblementalhealth.com account (Netlify Identity, Google provider). Each staff page then checks the person's role from the staff list. Planned to be set for Deploy Previews first, then Production at launch (which retires the shared password).

How it works:
- /staff-login sends people to Netlify Identity -> Google. Identity returns a token; /staff-login posts it in the request body to /api/staff-session (netlify/functions/staff-session.mts), which checks it with Identity at the site's main address (env URL; preview addresses are password-protected). Don't send the token as an Authorization header or nf_jwt cookie: on protected previews Netlify failed those requests with "Internal Error" before the function ran (Oct 2026). The function, accepts only @tangiblementalhealth.com Google accounts, and sets a signed httpOnly cookie tt_session for 7 days (SESSION_DAYS in netlify/lib/staff-session.ts). After 7 days people sign in with Google again, so a suspended work email loses access within 7 days at most; clicking Remove at /staff-admin cuts access within about a minute.
- Identity itself does not block personal Google accounts (Identity event functions caused "Failed to handle signup webhook" errors in Oct 2026 and were removed); /api/staff-session rejects them instead, so a personal account can never get a staff session.
